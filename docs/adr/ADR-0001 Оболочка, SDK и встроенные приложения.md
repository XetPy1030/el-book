# ADR-0001 Оболочка, SDK и встроенные приложения

**Тип:** ADR · **Аудитория:** владелец проекта, разработчики платформы, ИИ-агенты · **Статус документа:** живой · **Актуально на:** 19.10.2026

**Статус решения:** принято как рабочее 19.10.2026, владелец может пересмотреть · **Действует в коде с:** 20.10.2026

**Когда читать:** решаете, где живёт код нового приложения, как оно запускается и что ему разрешено трогать.

---

## Контекст

Владелец хочет «лаунчер-платформу»: быстрый удобный лаунчер и возможность дописывать
приложения — рисовалку, игры, полезные утилиты, возможно Telegram-клиент. Открытый вопрос
постановки — один лаунчер под все приложения или общая библиотека
([исходная постановка](../external/Исходная%20постановка.md)).

Ограничения:

- одно ядро около 1 ГГц и 512 МБ ОЗУ ([снимок устройства](../reference/Устройство%20Kobo%20Forma%20—%20снимок%2019.10.2026.md));
- всё, что раньше делал Nickel, — сон, USB, Wi-Fi, подсветка — кто-то должен делать за него, и
  ровно один процесс может владеть экраном и вводом в каждый момент
  ([жизненный цикл](../explanation/Жизненный%20цикл%20приложения%20на%20Kobo.md));
- разработчик один, приложения пишутся в одном репозитории;
- «быстрый» — главное требование к лаунчеру.

## Решение

**Оболочка + SDK + приложения, встроенные в оболочку.** Три слоя в одном Go-модуле:

1. **SDK** — пакеты, которые знают устройство и e-ink: экран и стратегия обновления, ввод и жесты,
   виджеты, шрифты, хранилище, журнал. Код устройства — за интерфейсами; у них две реализации:
   Kobo и эмулятор ([ADR-0004](ADR-0004%20Эмулятор%20устройства%20в%20браузере.md)).
2. **Оболочка** — единственный процесс на книге. Владеет устройством: останавливает и возвращает
   Nickel (через скрипт запуска), усыпляет, обрабатывает USB, держит статус-бар и быстрые
   настройки, показывает домашний экран и запускает приложения.
3. **Приложения** — Go-пакеты, реализующие контракт приложения из SDK и зарегистрированные в оболочке.
   Приложение получает экран, события и своё хранилище; к устройству напрямую не обращается.

Контракт проектируется так, чтобы позже приложение можно было запустить **отдельным процессом**
по тому же интерфейсу (описание-манифест плюс протокол поверх stdin/stdout или сокета), — это
этап расширения платформы в [плане](../decisions/План%20разработки.md). Первым кандидатом станет
Telegram-клиент, если его память или падения начнут мешать остальным.

Скелет контракта — для понимания формы, не код репозитория:

```go
// Манифест — то, что оболочка знает о приложении до запуска.
type Manifest struct {
	ID           string // "draw"
	Title        string // "Рисовалка"
	Icon         image.Image
	Orientations []Orientation
}

// App запускается оболочкой и отдаёт первый экран.
type App interface {
	Manifest() Manifest
	Start(ctx Context) Screen
}

// Screen рисует себя и обрабатывает события; оболочка решает, когда и как обновить панель.
type Screen interface {
	Draw(c *Canvas)
	Handle(ev Event) Command
}
```

## Рассмотренные варианты

| Вариант | За | Против | Итог |
|---|---|---|---|
| **А. Монолит без границ** — лаунчер и приложения одним кодом | проще всего начать | нет платформы: каждое новое приложение лезет в общий код | отвергнут |
| **Б. Оболочка + встроенные приложения** | переключение мгновенное: нет запуска процесса, повторной инициализации экрана и ввода, повторной загрузки шрифтов; один артефакт сборки и деплоя; одна точка, отвечающая за сон, USB и Wi-Fi; паники в чистом Go перехватываются по приложению | все приложения пересобираются вместе; один процесс на всех по памяти; стороннее приложение без пересборки не добавить | **выбран** |
| **В. Лаунчер + отдельные бинарники на общей библиотеке** (модель rmkit/remux, vlasovsoft) | изоляция падений и памяти; приложения выпускаются независимо; можно писать на чём угодно | запуск приложения — новый процесс и повторная инициализация; передача экрана и ввода между процессами; дублирование шрифтов и кэшей в памяти; каждое приложение должно само корректно отпускать устройство | отложен: как режим запуска для отдельных приложений |
| **Г. Встраиваться в Nickel** (NickelMenu, NickelDBus) | не нужно останавливать Nickel | у Nickel нет API для собственного экрана; рисовать поверх него ненадёжно | отвергнут |

Как устроены проекты-образцы — в [обзоре существующих проектов](../reference/Существующие%20проекты%20—%20снимок%2019.10.2026.md#rmkit-и-vlasovsoft--образцы-платформы).

## Последствия

- Добавить приложение — завести пакет, реализовать контракт, зарегистрировать в оболочке.
- Падение приложения не должно ронять оболочку: SDK запускает код приложения под `recover`,
  а горутины приложения — только через обёртку SDK, иначе паника в чужой горутине убьёт процесс.
- Если оболочка всё же упала, Nickel поднимает скрипт запуска
  ([ADR-0003](ADR-0003%20Запуск%20поверх%20Nickel%20через%20NickelMenu.md)).
- Тяжёлые зависимости одного приложения (например, Telegram) увеличивают общий бинарник.
  На книге 8 ГБ, но время старта оболочки измеряется и не должно выходить за
  [требования](../decisions/Требования%20к%20продукту%20v1.md#нефункциональные-требования).

## Когда пересмотреть

- Приложение регулярно съедает память или процессор, мешая остальным, — перевести его в отдельный процесс.
- Появились приложения от других авторов, которым нужен выпуск без пересборки оболочки.
